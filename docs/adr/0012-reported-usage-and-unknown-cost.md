# 累计已报告用量，不把未知解释为零

## 用量从哪里来

润色的每一次阶段调用都是一次模型请求。适配器在返回结果时一并上报这次请求的用量；请求以错误结束时，错误对象也可能带着已消耗的用量。core 只做两件事：把上报的数值累加进本次润色的总量，并记录“发起了几次调用、其中几次拿到了报告”。适配器没报的数字，core 不推断。

## 为什么失败与重做也计入

失败、取消、格式修复都会真实消耗模型资源。只统计最后成功的那次请求，会让“改了三遍才通过”看起来和“一次通过”一样便宜。所以失败结果同样携带已累计的用量；同一请求被适配器重复上报的快照由适配器去重，core 只负责相加。

## 为什么分成 unknown、partial、complete

三个状态回答的是“这次润色有多少次调用拿到了报告”：

- `unknown`：一次报告都没有，包括全部失败且无用量。
- `partial`：有报告，但不是每次调用都有。
- `complete`：每次发起的调用都返回了用量对象。

一次全零的用量也算有效报告——`0` 与“没给”是两回事，否则成功的调用会被误判成未知。费用同理：没有报就保持缺失，不估价、不补零暗示免费。

这三个词描述的是 core 收到的适配器报告，不是供应商账单。它不能证明取消没有计费，也不能反推供应商内部拆成了几次请求。

## 已知损失

CLI 经 pi-ai 取用量，而 pi-ai 会把缺失的用量补成零。因此 CLI 的 `complete` 只意味着“每次调用都返回了用量对象”，分不清上游真的消耗为零还是根本没有上报；价格未配置时也不输出零费用。

格式修复会增加一次调用计次，但它不是网络重试。CLI 显式关闭自动重试，dsh 适配器不额外重试，Pi 的重试选项交给宿主解释——所以 `complete` 始终相对于“core 实际发起的调用”，而不是供应商眼里的一次请求。

Pi 宿主要求费用字段时，只在适配边界补齐宿主形状，不写回 core 的未知状态。字段、累加口径与诊断规则见 [Core 文档](../../packages/core/README.md#模型适配) 和 [CLI 结果约定](../../packages/cli/README.md#模型协议与结果约定)；报告完整性由 `packages/core/src/polish.ts` 计算，公共用量运算位于 `packages/core/src/usage.ts`。
