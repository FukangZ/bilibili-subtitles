# 原子发布新产物，并在保存前复核输入

下载和润色可能重做，也可能并发写同一目标。模型运行时用户还可能编辑字幕。因此产物一律创建新文件：完整内容准备好才发布，重名自动编号，不覆盖既有字幕或文章；润色保存前重新读取输入，字节变化则拒绝保存，避免将基于旧输入生成的结果误认为当前输入的文章。

## 为什么不能先判断不存在，再普通写入

检查与写入之间存在竞争，普通写入还可能暴露半篇内容。默认 Node 实现先写同目录临时文件，再用硬链接发布到未占用的名称；`FileStore.createIfAbsent` 要求所有适配器保持原子完整、非覆盖的创建语义：成功返回 `true`，目标已存在返回 `false`，其他失败直接抛出。名称占用可以继续编号，权限或存储失败不能伪装成碰撞。

这保留了可比较的旧结果，却会增加文件数量；再次润色也不会隐式命中缓存，失败后重做可能再次计费。凭据和配置需要合法更新，使用各自的原子替换规则，不受产物“只能创建新文件”的限制。

## 保证的边界

保存前比较输入字节而非只看时间戳，能发现已发生且仍可见的修改，但没有锁住输入，不是从复核到发布的跨文件事务。`MutationQueue` 只协调关键操作，不能替代原子创建，也不自动提供跨进程锁。

输入输出路径必须相对传入的工作目录，规范化后不得在字面上越出该目录；这只检查路径组成，不防护恶意工作目录中的符号链接逃逸。默认实现依赖文件系统硬链接，不承诺断电持久性。dsh 通过宿主文件接口实现同一创建契约，不能绕过宿主权限。
