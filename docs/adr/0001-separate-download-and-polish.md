# 下载与润色分离，以可编辑字幕文件衔接

## 两个步骤各做什么

**下载**读取视频信息与指定分 P，选中文字幕轨道，把字幕整理为带起始时间的行，连同 YAML 元数据写入 Markdown。它只发 B 站请求，不调用模型，因此没有模型延迟与费用；产出的文件本身就能用：来源、标题、作者、发布时间、互动统计快照和全部台词都在里面。

**润色**读入这份原始字幕，先由模型确定文章标题与章节边界，再在已确定的范围内加工正文，最后校验、计算时间链接并组装保存（见 [0002](0002-two-stage-full-transcript-polishing.md)、[0003](0003-video-links-from-subtitle-boundaries.md)）。它是唯一调用模型的步骤：慢、按量计费，并把字幕全文发给模型提供方。

## 为什么分成两步

原始字幕已经能回答“这段视频讲了什么”，润色只改善可读性，不新增信息。把润色设为必经路径，等于让只想拿到文本的人一并承担等待和费用。

两步消耗的资源也不同：下载依赖 B 站登录态与网络；润色只读本地文件，依赖模型凭据，并把内容发往模型提供方。合成一次调用会绑定两套信任边界和两份预算，用户无法只提供其中一个。

两者的失败也是两类问题：没有中文字幕、未登录、Cookie 过期，与模型不可用、输出超长、结构校验不通过。分开后各自重试即可，一次模型失败不会让已下载的字幕作废。

既然它们是两次独立操作，衔接物就必须能跨进程、会话和入口存活，并允许用户中途检查和修改；因此下载直接交付可编辑的 Markdown 文件，润色只以该文件为输入。文件以 YAML 元数据保存视频来源、分 P 与字幕轨道，正文每行是一条带起始时间的字幕，如 `03:12 这里开始介绍下一部分`，无需专用编辑器即可检查和校正。

文件用 `kind: bilibili-subtitle` 标识原始字幕；生成文章则使用 `kind: bilibili-polished-article`，不能再次充当原始字幕输入。润色以实际读入的内容为准，不重新联网取得字幕或刷新统计；这使人工修改可以直接参与处理，代价是元数据与统计快照可能过时。

分离还让调用方自行编排：先收集多个视频再挑值得润色的，或先人工校正错字再润色。项目不提供内置批量调度。

## 为什么只处理现有中文字幕

外语字幕要先翻译再润色：多一个阶段，目标也从“忠实原文”变成“译本加润色”，错误来源和费用都随之变化。因此当前只处理中文轨道，缺失时明确失败，不自动下载媒体、识别语音或翻译；这些补救会悄悄改变内容来源与成本。翻译不在本决策范围内。

下载不消耗润色模型用量，但发起工具调用的主 Agent 对话仍有成本；独立选择模型的理由见 [0006](0006-independent-polishing-model.md)。
