# 用 monorepo 协同修改，以独立包交付不同入口

## 为什么同仓库、多包

core 的字幕格式、模型请求契约和错误语义会同时影响多个适配器。采用 monorepo（同一仓库管理多个包），可以在一次可审阅的变更中同步修改契约、实现、测试和文档，避免多个仓库之间逐个协调版本后才能验证。

但使用 CLI 的人不应安装整个 Agent 宿主，Pi 与 dsh 用户也只需要自己的入口。因此仓库使用 npm workspaces 管理 core、Pi、CLI、dsh 四个包，保持依赖方向从适配器指向 core，而不是合成一个包含所有宿主依赖的大包。

## 为什么不统一所有包的版本与发布

共享修改可以一起验证，但不表示所有包都要同时发布。core 与各适配器独立版本、按包 tag 发布；有 core 变更时先发布 core，再发布依赖新契约的入口。这样宿主特有的修复不强迫其他用户升级，代价是维护者必须核对依赖范围与发布顺序。

workspaces 链接会让本地开发更方便，也可能掩盖漏打包、内部导入或宿主依赖泄漏。因此跨包只使用公开入口，core、CLI 与 dsh 服务端交付编译后的 ESM；Pi 自身按宿主约定加载 TS 入口。源码在同一仓库不等于已安装包可以直接读取彼此的内部文件。

## 接受的成本

相较于独立仓库，根目录工具和锁文件更集中，全仓验证还需要准备 Pi peer；相较于单包，构建、打包和按包发布更复杂。修改依赖边界时，需要用不安装 Pi 的临时消费项目验证 core 和 CLI，不能只凭 workspace 测试判断发布包完整。
