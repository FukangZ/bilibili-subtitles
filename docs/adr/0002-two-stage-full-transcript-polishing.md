# 先提取整体结构，再按章节加工全文正文

## 两个阶段各做什么

**结构阶段**读完整原始字幕，返回文章标题、章节标题和各节起始条目 id。代码校验起点合法、严格递增，并据此生成连续、无重叠且覆盖全部条目的范围。

**正文阶段**把已确定的章节结构与按章节组织的完整字幕放进一次请求，得到各节正文。代码再校验节 id、顺序与数量，计算[原片跳转链接](0003-video-links-from-subtitle-boundaries.md)，组装标题、元数据与 Markdown 外壳。

## 为什么先定结构，再写正文

字幕按播放时间切片，不是文章段落。若让一次自由改写同时决定章节并加工语言，来源对齐与语言处理会互相干扰，章节是否覆盖输入也难以核查。所以先把边界固定下来，再在确定范围内合碎成篇、纠错和分段：模型负责语言内容，代码负责节 id、结束边界、时间、元数据和 Markdown 外壳，两侧可以分别校验。

## 为什么两阶段都用全文

当前模型能直接处理整份字幕文件，一次给全文比切块更简单，上下文也更充分：划分章节需要看到完整讲述结构，跨章节的措辞与术语一致也需要通读全文。代价是全文进入两次上下文，受模型输入与输出长度限制，结构阶段成功不保证正文能生成完；当前没有分块、阶段缓存或断点续跑，也不以静默截断或摘要绕过超限。

## 格式修复与校验

每阶段仅在 JSON 解析或结构校验失败后最多修复一次，因此通常两次、最多四次 core 阶段调用。无限重试会放大成本，所以修复有上限；网络错误、取消和适配器拒绝的截断不进入格式修复。接口没有强制 JSON Schema，校验仍可能失败。

校验能确认章节起点从首条开始且严格递增，范围连续、无重叠并覆盖全部条目，正文的节 id、顺序、数量与非空文本正确；它不能证明无遗漏、事实正确或语义忠实。忠实保留原意、论述次序、数字、广告和画面依赖是提示词目标，仍需读者审阅。

阶段与修复尝试由 core 显式传递给适配器用于诊断。具体契约见 [Core 模型适配](../../packages/core/README.md#模型适配)；编排与内容要求分别见 `packages/core/src/polish.ts` 和 `packages/core/prompts/`。
