# 将 B 站 Cookie 与普通配置分离

扫码取得的 Cookie 是登录凭据，不是偏好设置。若与模型设置混放，查看、编辑、备份配置都可能带出秘密；项目配置还可能把个人登录态带入仓库。因此 Cookie 只由适配器管理，采用独立用户级存储，不接受项目配置；core 只在下载时接收显式传入的凭据，不自行寻找用户文件。

Pi 与 CLI 各有独立用户级凭据文件，只存 Cookie，不隐式共用登录态；dsh 使用宿主凭据服务，浏览器不拿 Cookie。用户需要分别登录，但入口之间的授权来源更清楚，也减少普通配置操作碰到秘密的机会。

## 为什么迁移要先验证，再清理

旧配置迁移先建立并验证独立凭据，再移除旧字段，避免写入失败后丢失登录态。已存在且有效的新凭据优先，不被旧配置覆盖；损坏文件不能静默替换。普通配置更新不顺手复制未迁移 Cookie，而是要求先完成迁移。

重新登录需要更新当前凭据，因此采用原子替换，而不是像文章一样每次生成编号副本。Pi 与 CLI 先独占创建临时文件，完整写入后再原子重命名到凭据路径，避免失败时留下半份凭据；相关写入需进程内协调。dsh 登录与退出登录的并发约束见 [0008](0008-dsh-server-owned-capabilities.md)。

本地凭据文件以 `0600` 权限创建，新建父目录使用 `0700`，限制其他本机用户读取。读写目标须为普通文件，拒绝符号链接与损坏的 JSON，避免将异常目标当成可以直接覆盖的旧凭据；这些检查不构成对恶意文件系统并发替换的完整防护。

## 限制

独立文件避免引入统一操作系统密钥链依赖，但仍是明文存储，权限不等于加密，进程内队列也不是跨进程锁。CLI 模型 API key 仍在其敏感用户配置中，本决策不声称已经隔离所有秘密。
